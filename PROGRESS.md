- Real numbers verified on this machine (`tests/integration/calibration_smoke.cpp`, 3 runs): `B_P` ≈ 15–17 GB/s, `B_H` ≈ 11–13 GB/s. `B_P` being well below the RTX 4070's ~31.5GB/s PCIe ceiling is expected and informative — the calibration buffer is plain pageable memory, not pinned, which is a real, measured confirmation of why `HostResidentPool.use_mlock` (Module 3.2) matters.

- **Module 3.2 fix: real CUDA pinning, not just OS-level `mlock`.** The measured `B_P` numbers above prompted a closer look: `mlock()` only guarantees the OS won't swap a page out — it does NOT register memory with CUDA, so the GPU's DMA engine still couldn't transfer from it directly; CUDA was silently inserting a staging-buffer copy regardless of `mlock`. Fixed by switching `HostResidentPool` to `cudaHostAlloc()` (does both jobs in one call). Renamed `HostPoolConfig.use_mlock` → `pin_memory` since the code no longer calls `mlock()` at all. `ExpertSlot` gained a `pinned` bool so the destructor frees each slot with the correct matching allocator (`cudaFreeHost` vs `std::free`), since `cudaHostAlloc` failure falls back to `malloc` per-expert.
- Measured the real effect (`tests/integration/memory_smoke.cpp`, new `benchmark_pinned_vs_unpinned()`, 16MB transfer, 3 runs): unpinned 14–17 GB/s vs pinned 23–24 GB/s — a consistent ~40-60% real improvement on this machine.

Workaround: wrap in `bash -lc "cd / && /mnt/c/.../binary"` so the argument isn't a bare leading-slash token. Not a project bug, just a Git-Bash-on-Windows quirk when driving WSL2 from these tools.
- `perf`/hardware-counter fidelity under WSL2's custom kernel (`6.6.87.2-microsoft-standard-WSL2`) is unverified yet — flagged in `roadmap.md` §6 as a known risk; will confirm at the first profiling checkpoint (dev_spec.md §8 step 2).
- RESOLVED: FreeToken paper has now been fetched and read in full (see above) — the earlier flag about this being outstanding no longer applies.
- Timing alone is NOT a reliable way to distinguish a cache hit from a miss at this data size: once CUDA's one-time context-creation cost is paid (first call only, ~180ms), a genuine miss (tiny cudaMalloc+cudaMemcpy) can complete fast enough to look like a hit. Fixed by adding real `hits()`/`misses()` counters to `GpuExpertCache` rather than trusting elapsed-time heuristics — keep this in mind for any future benchmarking work (Section 5) that reasons about latency at small scale.
- SUPERSEDED (see Module 3.2 fix above, pool no longer uses `mlock`): `cudaHostAlloc` has its own scale concern to watch for later — pinned memory is a genuinely scarce OS resource, and pinning many GB (a real model's full expert set) can fail or degrade overall system performance, same category of tradeoff as the old `mlock`/ulimit concern, just a different specific limit. Untested at real model scale yet (only tested up to 16MB so far) — flagging so it isn't a surprise later.
