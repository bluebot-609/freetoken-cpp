[2026-09-19] [core/model_loader, Module 3.1] [third_party/ggml/src/gguf.cpp, verified with strace] — dev_spec.md §3.1 requires explicitly confirming whether ggml's GGUF loader uses `mmap` or `read()`. Answer: **`read()`, not `mmap`.** Code-level: `gguf_init_from_file` opens via `ggml_fopen`/`fopen` and reads via `fread` throughout (no `mmap` call anywhere in gguf.cpp). Confirmed at the syscall level too: `strace -e trace=openat,mmap,read ./build/src/cli/freetoken-cli tests/fixtures/hello.gguf` shows `openat("tests/fixtures/hello.gguf", O_RDONLY)` followed by exactly one `read()` of the full 128 bytes — no `mmap` on that file descriptor. (The build does show ~37 `mmap` calls overall, but those are dynamic-linker activity loading `libggml.so`/`libc.so` etc., unrelated to the GGUF file itself.)

Consequence for Phase 1's Host-Resident Pool (Module 3.2): there is no lazy page-in to reason about or override — `gguf_init_from_file(..., no_alloc=false)` eagerly pulls every tensor's bytes into process memory the moment it returns. The pool's `mlock`/`madvise` work in Phase 1 is about pinning/hinting memory ggml has *already* fully read in, not about intercepting a lazy mmap fault path the way an mmap-based loader (e.g. llama.cpp's own `llama_mmap`, built on top of ggml, not in ggml's core GGUF reader) would need to.

[2026-09-19] [build/CMake] [observed while wiring src/core/memory/gpu_cache] — `find_package(CUDAToolkit)`'s imported targets (`CUDA::cudart` etc.) did NOT turn out to be visible from `src/core/memory/CMakeLists.txt`, even though `third_party/ggml/src/ggml-cuda/CMakeLists.txt` already calls `find_package(CUDAToolkit)` earlier in the same configure run (confirmed by `-- CUDA Toolkit found` appearing in the log). CMake failed at generate time with "target was not found." Fix: call `find_package(CUDAToolkit REQUIRED)` ourselves in the root `CMakeLists.txt`, rather than relying on another subdirectory's internal call as a side effect. Lesson: don't assume a dependency another part of the build happens to need is safely shared — declare it explicitly wherever your own code needs it.

[2026-09-19] [roadmap/dev_spec, Module 3.4 + 3.6] [Yang, Fan, Pan, Xi, Wang, Sun, Keutzer, Han, Zaharia, Xu, Stoica. "FreeToken: Efficient Edge-Native MoE Serving with Bandwidth-Adaptive Execution." arXiv:2608.16157v1, 17 Aug 2026. Saved locally at `docs/references/freetoken_arxiv_2608.16157.pdf` (16 pages). Read in full before starting Module 3.4, per dev_spec.md §8 step 5's prerequisite.] — Two corrections made to roadmap.md/dev_spec.md as a direct result of reading the primary source instead of relying on the earlier secondary summary:

1. **Novelty claim corrected.** roadmap.md §2a previously listed the hardware calibration pass as "the headline original contribution... not described in the paper." This is false. Paper §3.2: "The bandwidth parameters (B_H and B_P) are empirically profiled on the target hardware at deployment." Table 1's caption confirms all bandwidths were measured on deployed hardware. The calibration pass is a ported mechanism, same category as the q* split itself — not original. Corrected in roadmap.md §0 and §2a's table.

2. **q* mechanism description corrected.** Previously described (secondhand, imprecisely) as "splitting a token's compute between CPU and GPU." The actual mechanism (paper §3.2, Eq. 1–4): at each decode step, the set M of cache-missing experts (size m) is partitioned into a GPU-fill subset F (size q, transferred over PCIe) and a CPU-direct-execute subset C (size m-q, computed against the Host-Resident Pool), run concurrently, outputs merged exactly. Split size: q* ≈ m·(B_P/B_H) — a genuinely simple closed form, not a stretch goal requiring an interim threshold heuristic as dev_spec.md §9 previously assumed. Corrected in dev_spec.md §3.4 and §9; roadmap.md §0/§1 table updated to match.

Also confirmed still valid: the SSD prefetch tier extension (paper's expert pool is loaded from disk once at startup, never used as a prefetch/execution tier — genuinely absent from the paper) and the C++/ggml reimplementation claim.

[2026-09-19] [core/scheduler, Module 3.6] [own mistake, caught by ggml's assert] — Sizing `ggml_init_params.mem_size` by hand for `measure_cpu_bandwidth()` in `calibration.cpp`: budgeted only for the input tensor (`n_elements * sizeof(float) + 4096`), forgot that `ggml_scale()` allocates a second, same-sized output tensor in the same context, plus the graph structure itself needs headroom. Hit `ggml_new_object: not enough space` (needed ~33.5MB, had ~16.7MB). Same class of mistake as `model_loader.cpp`'s original context sizing — fixed the same way, with a generous flat margin (`2 * n_elements * sizeof(float) + 4MB`) rather than trying to compute the exact minimum again. Lesson: don't hand-compute ggml context sizes precisely; over-provision by a wide, cheap margin instead.

[2026-09-19] [core/scheduler, Module 3.6] [measured on this machine] — First real calibration numbers: `B_P` (PCIe H2D, unpinned host buffer) ≈ 15–17 GB/s across 3 runs; `B_H` (ggml CPU scale op, multi-threaded) ≈ 11–13 GB/s. `B_P` is noticeably below the RTX 4070's PCIe 4.0 x16 theoretical ceiling (~31.5GB/s) — expected, since the host buffer here is plain `std::vector<char>` (pageable memory), not `cudaHostAlloc`/pinned. This directly motivated the Module 3.2 fix logged below.

[2026-09-19] [core/memory, Module 3.2] [CUDA C++ Programming Guide § pinned memory (per dev_spec.md §3.2's citation); own measurement] — `HostResidentPool` originally allocated via plain `malloc` and optionally called `mlock()` (`use_mlock`). This was a real gap: `mlock()` is an OS-level guarantee only (page won't be swapped to disk) — it does NOT register the memory with CUDA, so the GPU's DMA engine still can't transfer from it directly; CUDA silently inserts an internal staging-buffer copy for any "pageable" host memory, pinned-by-mlock or not. Fixed by switching to `cudaHostAlloc()`, which does both jobs in one call (page-locks AND registers with CUDA for direct DMA). Renamed the config field `use_mlock` → `pin_memory` accordingly, since the code no longer calls `mlock()` at all. `ExpertSlot` gained a `pinned` bool so the destructor frees each slot with the allocator that actually produced it (`cudaFreeHost` vs `std::free` are not interchangeable), since `cudaHostAlloc` failure falls back to `malloc` per-expert, non-fatal, same tradeoff-surfaced-not-hidden pattern as before.

Measured the actual effect (`tests/integration/memory_smoke.cpp`, 16MB transfer, 3 runs): unpinned 14–17 GB/s vs pinned 23–24 GB/s — a consistent, real ~40-60% improvement on this machine, not a theoretical claim.

[2026-09-19] [core/scheduler, Module 3.4] [own mistake, THIRD occurrence — see the two entries above] — `worker_loop()`'s placeholder CPU compute in `qstar_scheduler.cpp` under-sized its `ggml_init_params.mem_size` with a size-relative formula (`2 * slot->size_bytes + 4096`) instead of a flat margin, same root cause as the two entries above. This one actually crashed at runtime (`ggml_new_object: not enough space, needed 83376, available 4128` — segfault) rather than just failing an assert, because it hit the tiny 16-byte test experts specifically: the formula happened to work fine for the 256KB benchmark experts in the same test run, masking the bug until a smaller input exposed it. Fixed with the same flat-margin approach as before: `std::max(2 * size, 2MB) + 1MB`. Pattern now confirmed three times — a size-relative ggml context formula is not a reliable habit; always reach for a large flat constant instead, checked with a range of input sizes (both tiny and large), not just one.

[2026-09-19] [core/scheduler, Module 3.4] [measured on this machine, tests/integration/qstar_scheduler_smoke.cpp] — First real end-to-end benchmark of the q* scheduler against the Modules 3.2/3.3 naive stall-and-copy baseline, per dev_spec.md's "benchmark immediately" instruction: 40 experts (256KB each, all missing), naive baseline 3.58ms vs q* split (q=10 fill / 30 compute, matching the formula exactly for these bandwidths) 1.21ms — **~3x faster**, real and measured, not projected. This is the first evidence the project's actual core mechanism (concurrent CPU/GPU dispatch beating synchronous stall-and-copy) works as designed.
